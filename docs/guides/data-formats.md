# Data Formats

This document describes every on-disk format and the time semantics. The single source of truth for
table/column names is [miband_monitor/storage/schema.py](../../miband_monitor/storage/schema.py).

## 1. Data directory

The default is `data/`:

```
data/
├── heart_rate.jsonl
├── steps.jsonl
├── imu.jsonl
├── spo2.jsonl              # produced by --sync-history
├── activity_history.jsonl  # produced by --sync-history
├── spo2_sleep.jsonl        # produced by --sync-sleep-spo2 (also writes the spo2_sleep table)
├── activity_summary.jsonl  # produced by --sync-history --sync-sports (workout summaries)
├── mi_band.db              # contains separate spo2_sleep / activity_summary tables
├── mi_band.db-wal / mi_band.db-shm
└── csv/                    # generated by --export-csv
    ├── heart_rate.csv
    ├── steps.csv
    ├── imu.csv
    ├── spo2.csv
    ├── activity_history.csv
    ├── spo2_sleep.csv
    └── activity_summary.csv
```

## 2. Time semantics

| Data | Meaning of `ts` |
|---|---|
| Live streams (heart rate/steps/IMU) | **computer receive time** (Unix seconds, float) |
| History sync (SpO2/activity/sleep SpO2) | **sample time recorded by the band** (minute/second precision) |
| JSONL/SQLite | both carry `ts` (float) + `iso_time` (UTC ISO-8601 milliseconds) |

Cross-source merging (e.g. dashboard backfill) sorts and de-duplicates by `ts`, but be aware that the two kinds of time mean different things:
for long-span analysis, use the SQLite `ts` and `iso_time` as the reference.

## 3. JSONL

One JSON object per line; common fields:

| Field | Type | Description |
|---|---|---|
| `ts` | float | Unix timestamp (seconds) |
| `iso_time` | string | UTC ISO-8601, millisecond precision, e.g. `2020-01-07T08:10:18.472+00:00` |

Stream-specific fields:

| File | Fields |
|---|---|
| `heart_rate.jsonl` | `bpm` |
| `steps.jsonl` | `steps`, `distance_m`, `calories` |
| `imu.jsonl` | `sensor_type`, `sequence`, `sample_index`, `x_raw/y_raw/z_raw`, `ax_g/ay_g/az_g`, `ax_ms2/ay_ms2/az_ms2` (one line per acceleration sample) |
| `spo2.jsonl` | `spo2` (%), `auto_measure` (0/1) |
| `activity_history.jsonl` | `kind`, `intensity`, `steps`, `heart_rate`, `unknown1`, `sleep`, `deep_sleep`, `rem_sleep` (one line per minute) |
| `spo2_sleep.jsonl` | `spo2` (unsigned), `duration`, `spo2_high/low`, `signal_quality`, `extend` (raw byte groups), `source` |
| `activity_summary.jsonl` | `end_ts`, `duration_s`, `kind_code/kind_name`, `steps`, `active_seconds`, `calories`, `distance_m`, `average/max/min_hr`, `average_pace_s_km`, `version`, `has_gps` (one line per workout) |

Example:

```json
{"ts": 1578384618.472809, "iso_time": "2020-01-07T08:10:18.472+00:00", "bpm": 72}
{"ts": 1578384618.462322, "iso_time": "2020-01-07T08:10:18.462+00:00", "sensor_type": 1, "sequence": 0, "sample_index": 0, "x_raw": 0, "y_raw": 0, "z_raw": 256, "ax_g": 0.0, "ay_g": 0.0, "az_g": 1.0, "ax_ms2": 0.0, "ay_ms2": 0.0, "az_ms2": 9.8066}
```

IMU conversion: int16 / 4096 LSB/g; `a*_ms2 = a*_g * 9.80665`.

## 4. SQLite

Database `data/mi_band.db` (WAL mode); all six tables use `id` as the primary key and index `ts`/`iso_time`:

| Table | Columns |
|---|---|
| `heart_rate` | `id, ts, iso_time, bpm` |
| `steps` | `id, ts, iso_time, steps, distance_m, calories` |
| `imu` | `id, ts, iso_time, sensor_type, sequence, sample_index, x_raw, y_raw, z_raw, ax_g, ay_g, az_g, ax_ms2, ay_ms2, az_ms2` |
| `spo2` | `id, ts, iso_time, spo2, auto_measure` |
| `activity_history` | `id, ts, iso_time, kind, intensity, steps, heart_rate, unknown1, sleep, deep_sleep, rem_sleep` |
| `spo2_sleep` | `id, ts, iso_time, spo2, duration, spo2_high, spo2_low, signal_quality, extend` |
| `activity_summary` | `id, ts, iso_time, end_ts, duration_s, kind_code, kind_name, steps, active_seconds, calories, distance_m, average_hr, max_hr, min_hr, average_pace_s_km, version, has_gps` |

Common queries:

```sql
SELECT datetime(ts, 'unixepoch'), bpm FROM heart_rate ORDER BY ts;
SELECT * FROM steps ORDER BY ts;
SELECT sensor_type, sequence, sample_index, az_g FROM imu WHERE ts > :since;
SELECT datetime(ts, 'unixepoch'), spo2, auto_measure FROM spo2 ORDER BY ts;
SELECT datetime(ts, 'unixepoch'), steps, heart_rate FROM activity_history ORDER BY ts;
SELECT datetime(ts, 'unixepoch'), spo2, duration FROM spo2_sleep ORDER BY ts;
SELECT datetime(ts, 'unixepoch'), kind_name, steps, distance_m FROM activity_summary ORDER BY ts;
```

`spo2_sleep` is a **separate table** and is not mixed with spot-check `spo2`; the four byte groups whose semantics
are not yet understood are stored as JSON text.

An **empty** spot-check `spo2` table is expected behaviour: spot-check records exist only when a manual/automatic
single measurement was taken on the band; when there is none, the sync round simply "declares 0 records"
(visible as an INFO log line), which is not a link failure. For a continuous overnight curve use
`--sync-sleep-spo2` (written to `spo2_sleep`).

## 5. CSV

```bash
python export_csv.py --db data/mi_band.db --output data/csv
```

Exports the six tables above; the header is the column names, UTF-8 encoded, with `newline=""` (Windows compatible).
`--export-csv` performs the same export automatically when the session ends; it requires `--storage sqlite|both`.

## 6. History payload format (protocol layer)

| Type | Layout |
|---|---|
| Normal SpO2 `0x25` | version 2 + N×65B: `int32 LE unix_ts, int8 spo2, 60B reserved`; negative value = automatic measurement, real value +128 |
| Activity `0x01` | N×8B: `kind, intensity, steps, heart_rate, unknown1, sleep, deep_sleep, rem_sleep` |
| Sleep SpO2 `0x26` | version 2 + N×30B: `int32 LE ts, u8 spo2, u8 duration, 6B high, 6B low, 8B signal, 4B spare` |

The three activity bytes `sleep/deep_sleep/rem_sleep` are **not stage durations**, but discriminant scores computed by the band;
this project keeps them as evidence verbatim and derives sleep staging separately (see [modules/sleep.md](../modules/sleep.md)).

## 7. Derived data

Sleep results do not add a database table: `sleep_analysis.py` reads samples from `activity_history`
and outputs derived fields in reports/JSON/offline dashboards, with "derived value" semantics. The `DATA` object
embedded in the offline dashboard HTML is a presentation-layer payload and is not a long-term storage format.

## 8. Compatibility

- JSONL is append-only; SQLite schema changes must provide a migration and must not silently drop columns;
- When an old database lacks a table, analysis/dashboards degrade to "no data" instead of crashing;
- 255 is the heart-rate "no measurement" sentinel and must be filtered from all statistics; the valid SpO₂ range is 50–100.
